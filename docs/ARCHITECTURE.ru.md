# Архитектура и проверки-шлюзы

> Оригинал на китайском: [ARCHITECTURE.md](ARCHITECTURE.md) · English version: [ARCHITECTURE.en.md](ARCHITECTURE.en.md)

Этот документ — для сопровождающих: как переходят состояния, как решают пять проверок-шлюзов, как сочетаются блокировка и повторные попытки и почему страница плавающего окна обязана оставаться из одного источника с карточкой.
Руководство для пользователей — в [README](../README.md).

## 1. Три точки входа и поток данных

Корень этого репозитория — это и есть каталог плагина; сторона хоста и клиентская сторона делят его пополам:

| Файл | Ответственность |
| --- | --- |
| `lib/index.mjs` | Сторона хоста: проверки-шлюзы, отсчёт, вызов `shutdown.exe`, повторы и приостановка выключения, сохранение профиля, HTTP-маршруты, генерация страницы плавающего окна |
| `lib/client.js` | Карточка на боковой панели: единый бандл, CSS и React внутри него |
| `lib/i18n.mjs` | Тексты на трёх языках и разбор языка (`LANGS`, `resolveLang`) |
| `cordis.patch.yml` | Заводской patch внутри пакета плагина (низший приоритет) |

Поток данных — односторонняя цепочка опроса, без проталкивания:

```
Состояние хоста (снимок + события)
      │  GET /state?since=<ms>  (карточка и страница окна опрашивают независимо)
      ├──▶ Карточка на боковой панели (lib/client.js)
      └──▶ Страница плавающего окна (windowHtml() в lib/index.mjs)
```

`/state` заодно возвращает `ui` (variant / theme / lang); страница окна читает его каждую секунду и перерисовывается, поэтому при смене настройки окно меняется вместе с ней, без обновления страницы.

## 2. Шесть состояний работы

| Состояние | Значение | **Метка** карточки |
| --- | --- | --- |
| `off` | Не включено, ничего не отслеживается | `OFF` |
| `armed` | Режим включён, условия выполнены, ожидание следующей партии задач | `ARMED` |
| `hold` | Ожидание завершения фоновых задач | `WAIT` |
| `fire` | Идёт отсчёт, действие **ещё не отправлено**, уходит только в нулевой момент | `FIRE` |
| `fired` | Действие отправлено, отменить нельзя | `DONE` |
| `blocked` | Блокировка (два подсостояния: `halted` или `waiting`) | `PAUSED` |

Переходы:

```
off ──включение режима──▶ armed ──есть фоновые задачи──▶ hold ──задачи завершены──▶ armed
                │                                                      │
                └──условия выполнены и нет отсчёта──▶ fire ──отсчёт завершён──▶ fired
                │
                └──блокирующая ошибка──▶ blocked ──восстановление──▶ armed
```

- Все действия выполняются **inline**: отсчёт ведёт сам плагин, в нулевой момент команда уходит ровно один раз, а отправка означает немедленное выполнение. Отмена во время отсчёта = **ничего не отправляется**; после отмены режим **остаётся включённым**, и по завершении следующей партии задач действие всё равно сработает.
- Цена: если во время отсчёта DSH убьют или он упадёт, действие **не** выполнится. Старая реализация использовала системный таймер (`shutdown /t N`), и в таком случае выключение всё равно происходило; теперь всё «происходит, только пока плагин жив».
- После `fired` автоматического повторного включения нет — человеку нужно нажать ещё раз.

## 3. Пять проверок-шлюзов

В состоянии `blocked` действие не отправляется вовсе; во всех остальных случаях все пять условий должны выполняться одновременно (по умолчанию `shutdown`, но это может быть и перезагрузка / сон / выход из системы / загруженный пользователем скрипт):

| # | Шлюз | Поле | По умолчанию |
| --- | --- | --- | --- |
| 1 | Режим включён (нажато вручную человеком) | — | — |
| 2 | Нет запущенного отсчёта (чтобы не отправить дважды) | — | — |
| 3 | Все root-сеансы простаивают, ни один agent ещё не работает | — | — |
| 4 | Нет выполняющихся / останавливающихся фоновых задач | `blockOnJobs` | `true` |
| 5 | В этой партии ни один сеанс не сообщил об ошибке | `onlyOnSuccess` | `true` |

Если не хватает хотя бы одного условия, выключения не будет, а причина записывается в карточку и на вкладку «Статус» страницы настроек (полный поток — в `data/events.log`).

`marginSec` (по умолчанию 5 секунд) **не участвует в пяти проверках** и никак не связан с системными таймерами: все действия выполняются inline, команда уходит строго в момент окончания отсчёта. Он определяет лишь, сколько ещё карточка показывает состояние отсчёта, — состояние `fired` выставляется только через `countdownSec + marginSec + 5` секунд, и эти 5 секунд — фиксированная величина.

Если в этот период удержания нажать «Отменить выключение», команда уже покинула процесс и отозвать её нельзя; в журнал событий попадёт запись «действие отправлено, отменить невозможно».

Поэтому `marginSec` даёт время увидеть факт «уже отправлено», а не буфер для команды; увеличение лишь позже переводит карточку в «отправлено».

## 4. Состояние блокировки

При ошибке, которую нельзя обработать как обычный сбой, плагин **не снимает режим**, а только меняет цвет карточки и указывает причину:

| Подсостояние | Цвет | Триггер | Восстановление |
| --- | --- | --- | --- |
| `halted` | серо-синий | нехватка квоты, недействительные учётные данные, превышение контекста, неподдерживаемая возможность, диск заполнен | только человек: нажать «Снять и повторить» |
| `waiting` | серо-зелёный, пульсирующая точка | ограничение частоты, 5xx, обрыв сети, пустой ответ, тайм-аут, выгрузка изображения | автоматический повтор по стратегии; по наступлении внедряется инструкция «продолжить исходный план» |

Ритм повторов — в [CONFIG](./CONFIG.md), раздел 6.

**На диск сохраняется только `halted`** (`parked` в `config.json`): у `waiting` есть таймер и он самовосстанавливается, а сохранение превратилось бы в «после перезапуска ждём вечно».
Границы очистки: очищается при включении режима, снятии, успешном ходе, срабатывании `shutdownOnHalt`; **не** очищается при перезапуске, смене профиля, смене языка и смене оформления — всё это не меняет факта «эта партия уже приостановлена».
Выполняется ли действие после приостановки, решает `shutdownOnHalt`, а его действующее значение зависит ещё и от главного переключателя `onlyOnSuccess` (см. [CONFIG](./CONFIG.md), раздел 2).

## 5. Автоматическое перехватывание при AFK

Действует только пока режим включён; три вещи:

1. **Автоматический ответ на вопросы** (`afkAutoAnswer`, по умолчанию включено): отвечает «пользователь в AFK, сначала завершите уже поставленные задачи, сведите отчёт и сохраните его на диск, не трогайте ветки, которых не поручали», возвращает `selected: []` плюс собственный текст и **не выбирает за пользователя ни один вариант**; если выключить, вопросы снова показываются пользователю.
2. **Восстановление после ошибок**: при ошибке сеанса у agent сначала просят разобраться и продолжить исходный план; при повторном сбое в том же сеансе — «прекратить повторы, написать отчёт и завершить».
3. **Защита от прерывания**: если пользователь вручную останавливает задачу на полпути, выключение не срабатывает.

## 6. Плавающее окно и боковая панель: MIRROR CONTRACT

Страница окна генерируется на стороне хоста (`windowHtml()` в `lib/index.mjs`), карточка — на клиенте (`lib/client.js`).
Это **две отдельные реализации отрисовки**, и любая общая логика отображения должна меняться с обеих сторон. Ниже исходное ограничение из `lib/index.mjs` (сохранено дословно):

> MIRROR CONTRACT — this page is a *copy* of the card, not a reference to it:
> whenever lib/client.js changes a variant body, a theme token, a state colour
> or a card string, the same change must land here, and the comparison
> screenshots under `_ops/worklog/` must be regenerated. The card settings
> (variant / theme / lang) are held by the host and arrive in every `/state`
> snapshot as `ui`, so the 1s poll repaints this page when they change; the
> same localStorage keys are read once as a first-paint fallback because the
> sidebar and this window can sit in different storage partitions. `folded` is
> ignored on purpose — a floating window is always expanded.
>
> Counters belong to that contract as well: B's run dots (one per live agent, cap
> `DOT_CAP = 12`, `+N` badge, `role="img"` + `radar.aria`) and C's agent counter
> must stay same-source with lib/client.js's `syncDots()` / `unit.agent`. Both
> read `agentRunningTotal` (falling back to `runningCount`), never `runningCount`
> alone — otherwise a Team of subagents shows three dots in the sidebar and one
> here, which is the contradiction a user notices first.

Пояснения:

- На странице окна есть дополнительная строка статистики (в боковой панели её нет) — это **единственное** допустимое различие; `folded` намеренно игнорируется.
- «Компактный режим» плавающего окна хранится на хосте (`compact` в `data/ui.json`, по умолчанию включён); внутри окна переключателя нет.
- Три уровня отказоустойчивости записаны в разметку страницы: хост не подключён → заглушка; `/state` 5xx → сохраняется последний снимок и показывается офлайн; язык переключили в другом месте → события перезапрашиваются согласно `state.lang`.

## 7. Платформы и поверхность отказов

- **Платформы**: win32, macOS и Linux теперь подключаются по одному и тому же пути — в таблице действий для каждой платформы есть строка, а в `apply()` остался только один защитный ранний выход (срабатывает, лишь когда у платформы вообще нет строки `shutdown`; сейчас недостижим, а `log.platformUnsupported` остаётся в каталоге текстов).
  - **Три уровня реальной проверки**: Windows **проверен полностью, включая реальное выполнение**; на macOS **выключение проверено, машина действительно выключилась** (проверки-шлюзы → таймер/пересчёт → `spawn` → система приняла команду → питание отключилось; Apple Silicon / macOS 27.2 / DSH Desktop), **при условии, что ни одно приложение не блокирует выключение**; **перезагрузка / выход из сеанса / сон / гибернация на реальной машине не проверялись**; Linux **покрыт только кодом и проверками, на реальной машине не тестировался**.
  - Остановка на macOS — не вина плагина: система сначала смотрит, не заявило ли какое-то приложение «я занято», поэтому терминал с командой на переднем плане или редактор с несохранёнными документами заставляют её ждать подтверждения — так же, как при ручном «Выключить» из меню Apple; освободите передний план — и выключение пройдёт нормально. Чтобы выполнить безусловно, нужен root (`shutdown -h now`), а плагин намеренно не трогает повышение прав.
  - У macOS `lock` нет надёжного CLI (`displaysleepnow` только гасит экран, а ⌃⌘Q требует разрешения на универсальный доступ), поэтому он явно сообщает `unsupported-on-platform`, а не блокирует наполовину; у macOS `hibernate` нет пользовательской команды, и он деградирует до `pmset sleepnow`.
  - В Linux `signout` использует `loginctl terminate-user`, что завершает и сам DSH (DSH работает в сеансе этого пользователя).
  - На не-win32 у любого действия, для которого удаётся разрешить команду, доступность сообщается как `'unknown'`: TCC / polkit могут отказать в последний момент, и сообщить `true` было бы ложью. `actionReadyNow()` считает недоступным только `false`, поэтому `'unknown'` **можно взводить**: это значит, что решает всё ещё ОС, а не что что-то сломано.
- `app.asar` и исходники DSH не изменяются; всё подключается через слоты и события.
- Ноль runtime-зависимостей: серверная сторона использует только `node:fs` / `node:path` / `node:crypto`, браузерная — только `require('react')`.
- Логи идут через `log(message, kind)`, без `console.log`.

## 8. Ответственность каталогов

```
lib/          источник истины: хост, карточка, i18n
cordis.patch.yml  заводской patch
test/         утверждения (host.test.mjs / client.test.cjs)
scripts/      скриншоты, демо-страница, иконки, помощники выпуска
docs/         документация для сопровождающих: ARCHITECTURE, CONFIG, DEVELOPING, BETA, RELEASE-NOTES-STYLE; у первых четырёх есть китайская версия, перевод `.en.md` и перевод `.ru.md` (RELEASE-NOTES-STYLE только на китайском)
data/         runtime-данные (config.json / ui.json / events.log / scripts/), не коммитятся
```

`data/scripts/` хранит загруженные пользователем скрипты выполнения, имена файлов — `<profileId>.<ext>`, их создаёт хост. Каталог **обязан быть вне пакета**: каталог npm-пакета при обновлении заменяется целиком и после установки обычно недоступен для записи, поэтому скрипты внутри исчезнут при следующем обновлении. Тело скрипта не попадает в `config.json`, в профиле остаются только метаданные: `sha256`, размер, отображаемое имя.

`preview/` — материал процесса проектирования, а не текущая реализация; `docs/screenshots/` — результат работы скриптов.
