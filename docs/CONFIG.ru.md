# Поля конфигурации

> [中文](CONFIG.md) · [English](CONFIG.en.md) · **Русский**

Для сопровождающих и для тех, кто хочет править конфигурацию вручную. Пользовательское описание настроек — в [README](../README.md).
Мотивация логики проверок-шлюзов и повторов — в [ARCHITECTURE](./ARCHITECTURE.md).

## 1. Три источника и их приоритет

От низшего к высшему:

1. `cordis.patch.yml` — заводской патч внутри пакета плагина
2. `data/config.json` — сохраняется во время работы; сюда попадает всё, что меняют на странице настроек
3. `POST /config`, `POST /ui` — изменения во время работы, они тоже записываются на диск

Страница настроек не обходит второй уровень: каждое её изменение проходит через ту же функцию записи на диск (`saveStore()`).

## 2. Структура `data/config.json`

```json
{
  "version": 5,
  "activeProfileId": "default",
  "customEnabled": false,
  "lastCustomProfileId": null,
  "language": "auto",
  "parked": null,
  "scriptSeq": 2,
  "scripts": [ { "id": "s1", "…": "…" } ],
  "profiles": [ { "id": "default", "…": "…" } ]
}
```

| Ключ верхнего уровня | Тип | По умолчанию | Описание |
| --- | --- | --- | --- |
| `version` | число | `5` | версия schema; v1.6.1 подняла её с 2 до 4, а библиотека скриптов — до 5 |
| `activeProfileId` | string | `default` | id действующего профиля |
| `customEnabled` | bool | `false` | разрешено ли использовать пользовательские профили |
| `lastCustomProfileId` | string \| null | `null` | тот профиль, к которому нужно вернуться после повторного включения |
| `language` | перечисление `auto` / `zh` / `en` / `ru` | `auto` | язык интерфейса; `auto` следует за системой |
| `parked` | объект \| null | `null` | картина приостановки выключения, см. `### parked` ниже в этом разделе; единственное **состояние времени выполнения**, записываемое в файл конфигурации |
| `scriptSeq` | число | `0` | выдаёт id скриптам и только растёт; удалённые id не переиспользуются |
| `scripts` | массив | `[]` | **общая для всего плагина** библиотека скриптов, в каждом элементе только метаданные, см. `### scripts[]` |
| `profiles` | массив | один `default` | каждый элемент — снимок поведения |

### `scripts[]`: общая библиотека скриптов

Раньше скрипт был полем одного профиля, теперь это **общая библиотека на верхнем уровне**: один файл — одна запись, любое число профилей ссылается на неё через `scriptId`, и одно подтверждение действует на все профили, которые на неё ссылаются.

```json
{
  "id": "s1",
  "name": "уборка в конце дня",
  "ext": "ps1",
  "file": "s1.ps1",
  "bytes": 412,
  "sha256": "9f2c…",
  "savedAt": 1762500000000,
  "ack": { "sha256": "9f2c…", "at": 1762500100000 }
}
```

| Ключ | Тип | Описание |
| --- | --- | --- |
| `id` | `s1` / `s2` … | выдаётся `scriptSeq`, никогда не переиспользуется; при чтении должен совпадать с `^s[1-9][0-9]*$`, иначе запись отбрасывается целиком |
| `name` | string | отображаемое имя, 1–40 символов; влияет только на интерфейс и никогда не попадает в путь |
| `ext` | перечисление `js` / `cmd` / `bat` / `py` / `ps1` | определяет, какой интерпретатор запускать |
| `file` | string | **должно** быть ровно `<id>.<ext>`, иначе запись отбрасывается — правка конфигурации руками не может направить запуск по произвольному пути |
| `bytes` | число | размер файла, только для отображения |
| `sha256` | 64 шестнадцатеричных символа | хеш содержимого на момент сохранения; к нему привязано подтверждение |
| `savedAt` | число | когда запись попала в библиотеку |
| `ack` | объект \| null | `{ sha256, at }`; при чтении отбрасывается, если его `sha256` больше не совпадает с записью (считается неподтверждённым) |

- Само тело хранится **только** на диске: `<DATA_DIR>/scripts/<scriptId>.<ext>`. Оно не попадает ни в `config.json`, ни в журнал событий, ни в `/state`.
- Удалённый файл или файл, изменённый руками, не заставляет запись исчезнуть: в первом случае `custom` сообщает `no-script`, во втором — `script-not-acknowledged` (см. 4.5).
- В профиле хранится только `scriptId` (`null` — ничего не выбрано); полей `script` и `scriptAck` **больше нет**, их запись отклоняется с `400` (см. 4.1).

Внешний вид интерфейса (стиль карточки на боковой панели / тема / сворачивание / компактный режим плавающего окна) в этом файле **отсутствует**, см. раздел 7.

### `parked`: единственное состояние времени выполнения, записываемое в конфигурацию

```json
{ "code": "RATE_LIMIT", "level": "halted", "reasonKey": "halted.RATE_LIMIT", "at": 1762400000000 }
```

- **На диск попадает только `halted`**. У `waiting` есть таймер, и оно восстанавливается само; сохранённое значение превратилось бы в «после перезапуска ждём вечно».
- При чтении `code` должен входить в `HALTED_CODES`, иначе вся запись отбрасывается (`null`): неизвестный code отрисуется пустой причиной, а это хуже, чем забыть его.
- **Границы очистки**:
  - Очищается: включение режима, снятие, успешный ход, срабатывание `shutdownOnHalt`.
  - Не очищается: перезапуск, смена профиля, смена языка, смена внешнего вида — всё это не меняет факт «эта партия уже приостановлена».
- `parkedAt` в `/state` — его отметка времени (`null`, когда приостановки нет); по ней интерфейс показывает «последняя приостановка 3 часа назад».

### Действующее значение `shutdownOnHalt`

Переключатель на странице настроек — это производное значение `shutdownOnHaltEffective`, а главный переключатель — `onlyOnSuccess`:

| Условие | Действующее значение |
| --- | --- |
| `onlyOnSuccess: false` (главный переключатель выключен) | принудительно `false` |
| `onlyOnSuccess: true` | соблюдается сохранённое пользователем `shutdownOnHalt` |

**Сохранённое пользователем значение на диске никогда не перезаписывается**, поэтому переключение главного выключателя туда-обратно не теряет исходный выбор пользователя; когда главный выключатель выключен, страница настроек лишь делает элемент неактивным.

## 3. Поля profile

Каждый профиль хранит свою копию, они друг на друга не влияют.

| Ключ | Тип | По умолчанию | Описание |
| --- | --- | --- | --- |
| `countdownSec` | число 10–600 | `60` | секунды отсчёта перед выключением. **В профиле по умолчанию зафиксировано 60** |
| `marginSec` | число 0–60 | `5` | запас в секундах: дополнительное удержание после отправки команды, пока карточка на боковой панели не переключится в «отправлено» (плюс фиксированные 5 секунд); не сдвигает момент отправки команды и не связан с системными таймерами, см. ARCHITECTURE, раздел 3. **В профиле по умолчанию зафиксировано 5** |
| `onlyOnSuccess` | bool | `true` | пропускать, если какой-либо сеанс в этой партии сообщил об ошибке. **В профиле по умолчанию зафиксировано `true`** |
| `blockOnJobs` | bool | `true` | пропускать, если есть работающие фоновые задачи. **В профиле по умолчанию зафиксировано `true`** |
| `afkAutoAnswer` | bool | `true` | пока режим включён, отвечать на вопросы за пользователя и выполнять восстановление после ошибок. **В профиле по умолчанию зафиксировано `true`** |
| `notify` | объект | все четыре `true` | `{ countdown, fired, blocked, recovered }`, по булеву значению на каждый |
| `retrySec` | число 10–600 | `30` | резервный интервал повтора, когда не подошла ни одна именованная стратегия |
| `retryPolicies` | объект | см. раздел 6 | имя стратегии → `{ mode: 'backoff', base, max }` или `{ mode: 'fixed', every }` |
| `retryAssign` | объект | см. раздел 6 | код ошибки → имя стратегии |

**Новое в v1.6.1 (уже в schema)**

| Ключ | Тип | По умолчанию | Описание |
| --- | --- | --- | --- |
| `action` | перечисление (8 id) | `shutdown` | что выполнять по завершении задач, см. раздел 4 |
| `scriptId` | string \| null | `null` | какая запись общей библиотеки скриптов используется этим профилем; сам скрипт больше не хранится в профиле |
| `shutdownOnHalt` | bool | `true` | выполнять ли действие после приостановки выключения (`halted`) |

- `scriptId` имеет смысл только при `action: custom`; если файла нет, будет `no-script`, если он не совпадает с подтверждёнными байтами — `script-not-acknowledged`; подробнее в 4.3.
- Запись `script` или `scriptAck` в патче профиля отклоняется с `400`, см. раздел 5.
- `shutdownOnHalt: false` означает «после приостановки не действовать»; значение по умолчанию `true` совпадает со старым поведением (приостановка лишь перестаёт ждать условий и не меняет само действие).
- Все четыре входят в `PROFILE_PATCH_FIELDS`, поэтому задаются отдельно для каждого профиля. Обратите внимание: `shutdownOnHalt` **не входит** в зафиксированные поля профиля по умолчанию (зафиксированы `countdownSec`, `marginSec`, `onlyOnSuccess`, `blockOnJobs`, `afkAutoAnswer`), поэтому его можно менять и в профиле по умолчанию.

## 4. `action`: что делать в нулевой момент

Восемь id, **семь доступны**; `restart-dsh` перечислен, но неактивен.

**Видимость по умолчанию**: когда «пользовательские профили» не включены, список действий предлагает только выключение, перезапуск, сон и гибернацию; блокировка экрана, выход из системы и пользовательский скрипт управляются переключателем `customEnabled`. Именно его включение заставляет весь блок «пользовательский скрипт» (выбор файла, отображаемое имя, предупреждение и подтверждение) появиться на странице настроек. Если в каком-то профиле всё ещё сохранён `custom`, а переключатель уже выключен, в начале выпадающего списка остаётся неактивный пункт-заполнитель «Пользовательский скрипт (недоступен)»; он исчезает, как только значение меняется на любое действие из списка — иначе список выглядел бы пустым и ничего не сообщал.

| id | win32 | macOS | Linux |
| --- | --- | --- | --- |
| `shutdown` | `shutdown /s /t 0` | выключение через `osascript` | `systemctl poweroff` |
| `restart` | `shutdown /r /t 0` | перезапуск через `osascript` | `systemctl reboot` |
| `hibernate` | `shutdown /h` | нет пользовательской команды гибернации, **деградирует до сна** (`pmset sleepnow`) | `systemctl hibernate` |
| `sleep` | `rundll32 powrprof.dll,SetSuspendState` | `pmset sleepnow` | `systemctl suspend` |
| `lock` | `rundll32 user32.dll,LockWorkStation` | **не поддерживается** (нет поддерживаемого CLI) | `loginctl lock-session` |
| `signout` | `shutdown /l` | выход из системы через `osascript` | `loginctl terminate-user`, **завершает и сам DSH** (DSH работает в сеансе этого пользователя) |
| `restart-dsh` | **перечислен, но сейчас недоступен для выбора** | так же | так же |
| `custom` | выполняет **скрипт, выбранный из библиотеки** (см. 4.1) | так же | так же |

- Все действия **inline**: отсчёт ведёт сам плагин, в нулевой момент он **отправляет ровно один раз**, а отправка означает немедленное выполнение. Отмена = ничего не отправляется.
- Цена: если во время отсчёта DSH убит или упал, действие **не** выполнится. Старая реализация использовала системный таймер (`shutdown /t N`), и в этом случае выключение всё равно произошло бы. Это сознательный компромисс — лучше пропустить выключение, чем выключить не вовремя.
- Неизвестный `action` откатывается к `shutdown`: даже испорченная конфигурация не даст состояния «режим включён, но никакого действия нет».
- **Почему `restart-dsh` неактивен**: перезапуск DSH должен идти через `app.relaunch()`, а это возможность главного процесса Electron, до которой у плагина нет пути; `process.exit()` пропустил бы очистку хоста и мог бы повредить работающие сеансы, поэтому так сознательно не делается. Id сохранён, чтобы файл конфигурации оставался читаемым и его можно было включить сразу, как только хост откроет интерфейс.

### 4.1 Пользовательское действие = один файл, выбранный из библиотеки

`custom` не принимает командную строку; выполняется одна запись из **библиотеки скриптов**. Библиотека общая: одна загрузка — одна запись, и любое число профилей может на неё ссылаться.

```http
POST /config
{ "putScript": { "name": "Уборка в конце дня", "ext": "ps1", "content": "<тело скрипта>" } }
```

| Поле | Ограничение |
| --- | --- |
| `name` | отображаемое имя, 1–40 символов после обрезки пробелов; как бы оно ни называлось, путём оно не станет |
| `ext` | белый список `js` / `cmd` / `bat` / `py` / `ps1`, остальное — 400 |
| `content` | текст UTF-8, **не более 256 KiB** (считается в байтах, не в символах); при превышении — 400 |
| `profileId` | **необязательно**. Если задан, запись ещё и выбирается для этого профиля, а его `action` становится `custom`; без него запись только попадает в библиотеку |

- **Дедупликация**: запись с тем же `sha256` и тем же `ext` переиспользуется, в ответе приходит `reused: true`, а `name` существующей записи **не перезаписывается** (повторная загрузка не должна втихую переименовывать чужую запись).
- Если запись есть, а её файл на диске изменён руками или удалён, повторная загрузка того же содержимого **чинит файл**, а не создаёт вторую копию.
- Где хранится: `<DATA_DIR>/scripts/<scriptId>.<ext>`. **Не в каталоге npm-пакета**: каталог пакета при обновлении заменяется целиком и после установки обычно недоступен для записи; `DATA_DIR` — это записываемый каталог плагина (`config.json` и `events.log` тоже там).
- Имя файла формирует **хост** (`<scriptId>.<ext>`); пользовательский ввод не участвует в сборке пути, что исключает обход пути.
- Тело скрипта **никогда** не попадает в `config.json`, журнал событий или `/state` — там только метаданные.
- Всё тело запроса ограничено **1 MiB** (`BODY_LIMIT`): раньше `/config` нёс только небольшие патчи при 8 KiB, но скрипты идут как текст JSON и после экранирования растут примерно вдвое, поэтому лимит подняли; при превышении соединение просто обрывается, а не возвращается 413.

Остальные операции библиотеки тоже идут через `POST /config`, один ключ на запрос:

| Ключ | Тело | Поведение |
| --- | --- | --- |
| `selectScript` | `{ profileId, scriptId }` | выбрать запись для этого профиля (`scriptId: null` — снять выбор); при выборе `action` становится `custom`; неизвестный id — `400 unknown script` |
| `renameScript` | `{ scriptId, name }` | только отображаемое имя, 1–40 символов; `sha256` не меняется, подтверждение остаётся в силе |
| `deleteScript` | `{ scriptId }` | удаляет запись и её файл; **удалять можно и ту, которой ещё пользуются профили**, такие профили остаются без скрипта, а `affected` в ответе — сколько профилей затронуто |
| `ackScript` | `{ scriptId }` | фиксирует «я подтвердил это содержимое»; `ack` хост записывает по текущему `sha256` |
| `unackScript` | `{ scriptId }` | отзывает подтверждение |

Форма записи — см. `### scripts[]` в разделе 2. В профиле хранится только `scriptId`.

### 4.2 Сопоставление выполнения

| `ext` | Фактическая команда | Описание |
| --- | --- | --- |
| `cmd` / `bat` | `cmd /c <path>` | `CreateProcess` в Windows не выполняет файлы скриптов, нужна обёртка `cmd` |
| `ps1` | `powershell -NoProfile -ExecutionPolicy Bypass -File <path>` | не читает пользовательский профиль PowerShell; обход политики действует только для этого запуска |
| `py` | `python <path>`, с откатом к `python3` | если не найден ни один → `missing-interpreter` |
| `js` | `node <path>` | node не найден → `missing-interpreter` |

Обнаружение интерпретатора переиспользует проверку доступности действий (`subprocess.resolveExecutable`), результат попадает в `/state.actions.custom`. Если интерпретатора нет или скрипта нет, область действия показывает недоступность с причиной, а включение режима отклоняется.

### 4.3 Подтверждение привязано к байтам записи в библиотеке

Подтверждение принадлежит записи библиотеки (`scripts[].ack`), а не профилю:

- **Перед включением режима должно выполняться `ack.sha256 === sha256 этой записи`**, иначе включение отклоняется с причиной `script-not-acknowledged`.
- Как только содержимое записи меняется (повторная загрузка другими байтами), `sha256` меняется, и **прежнее подтверждение автоматически теряет силу** — нужно отметить заново. Изменение только отображаемого имени не влияет на `sha256`, подтверждение остаётся действительным.
- Если файл на диске изменён руками и байты больше не совпадают с записанным `sha256`, вы получите всё тот же `script-not-acknowledged` — подтверждается содержимое, а не имя файла.
- Подтвердили один раз — все профили, ссылающиеся на эту запись, считаются подтверждёнными; отозвали — теряют подтверждение все.
- Это защищает от «подтвердили один раз, а потом подменили файл» — подтверждение, действующее вечно после одной галочки, равносильно отсутствию подтверждения.

### 4.4 Проверка доступности действий и трёхзначное значение

Проверка выполняется один раз при монтировании, дальше только по `POST /config {recheck:true}`; **опрос не используется**. Каждый элемент `/state.actions` — это `{ available, reason }`:

| `available` | Значение |
| --- | --- |
| `true` | команда разрешается, и за ней нет других отсекающих звеньев (вроде `shutdown` в win32) |
| `false` | на этой платформе нет честной команды, команды не существует, нет интерпретатора, нет скрипта или мешает подтверждение |
| `'unknown'` | команда есть, но macOS (TCC) или Linux (polkit) могут отказать в последний момент — сообщать здесь `true` было бы ложью |

На не-win32 все разрешаемые команды сообщают `'unknown'`, а не `true`.
Если при повторной проверке **текущее выбранное действие** стало недоступным, хост только ставит отметку (`/state.actionReady === false`, карточка на боковой панели и страница настроек показывают подсказку) и **не меняет выбор пользователя**.

### 4.5 Перечисление `reason`

`/state` отправляет только строки протокола; страница настроек переводит их на человеческий язык.

| Значение | Когда появляется |
| --- | --- |
| `no-custom-profile` | когда «пользовательские профили» не включены, действия `lock` / `signout` / `custom` все недоступны |
| `no-script` | `action: custom`, но скрипт не выбран или файл выбранной записи удалён |
| `missing-interpreter` | скрипт есть, но ни `python` / `python3` / `node` / `powershell` не найдены |
| `needs-elevation` | для встроенных действий на не-win32: доступность сообщает `'unknown'`, причина — эта; команда найдена, но TCC / polkit могут потребовать авторизации. **Это консервативная пометка на случай «надёжно проверить нельзя», а не результат проверки**: не читайте её как «нужен sudo»; на реальном рабочем столе Ubuntu 24.04.5 LTS все шесть действий выполнились без дополнительных прав |
| `unsupported-on-platform` | на платформе нет честного способа (macOS `lock`) |
| `no-host-restart` | `restart-dsh`: до `app.relaunch()` Electron не дотянуться |
| `script-not-acknowledged` | подтверждения нет, либо подтверждённые байты больше не совпадают с тем, что на диске — включая файл, изменённый руками |
| `no-cli` | на этапе проверки исполняемый файл не найден (значение отказа `argvReachable`; сюда же попадают проблемы с иконкой/путём в macOS) |
| `no-session` | оставлено в перечислении, сейчас ни один путь его не выдаёт (старая ветка недоступного сеанса) |

Старое значение `no-custom-command` удалено (оно относилось к заменённой модели командной строки и никогда не публиковалось).

Граница `no-custom-profile`: его определяет только тот единственный переключатель, и к тому, «настроено ли что-нибудь», он отношения не имеет. `restart-dsh` всегда `no-host-restart` и **этим не затрагивается**; `custom` после включения переключателя, но без выбранного скрипта сообщает `no-script` — одно говорит «это действие сейчас не открыто», другое — «открыто, но вы ещё не подготовились», и путать их нельзя.

### 4.6 Какой эффект даёт каждый из четырёх видов скриптов в Windows

Пользователю нужно только выбрать файл из библиотеки и не писать никаких путей — путь формирует хост.

| Загруженное расширение | Что нужно на машине | Эффект типичного скрипта |
| --- | --- | --- |
| `.cmd` / `.bat` | ничего (`cmd.exe` есть всегда) | закрыть браузер, упаковать журналы, затем `shutdown /s /t 0` |
| `.ps1` | PowerShell | то же, но можно напрямую вызывать .NET / COM, например послать службе сигнал остановки |
| `.py` | `python` или `python3` | уведомить по HTTP, очистить временные каталоги |
| `.js` | `node` | разобрать локальные файлы, вызвать `fetch` и отправить сообщение |

Внимание: скрипты выполняются с **правами текущего пользователя**; плагин не проверяет содержимое и не гарантирует его безопасность — поэтому перед включением режима нужно подтвердить текст отказа от ответственности (см. 4.3).

### 4.7 Повтор с повышением прав в Linux

Этот слой есть только в Linux. Если одно из действий `shutdown` / `restart` / `sleep` / `hibernate` / `lock` / `signout` **впервые завершилось с ненулевым кодом**, хост повторяет его **один раз** через `pkexec`:

- `pkexec` запрашивает согласие у polkit и выполняет ту же команду от имени root, поэтому может появиться окно аутентификации; ожидание ограничено 120 секундами (для обычных действий — 15).
- Команда, завершившаяся с кодом 0, **никогда** не отправляется повторно — одно выключение не будет доставлено дважды.
- Скрипты `custom` **никогда** не повышают права: это собственный скрипт пользователя, он всегда работает от текущего пользователя.

Риск назван прямо: повтор исходит из того, что «ненулевой код» означает «не выполнилось». Если команда **уже произвела эффект, но всё равно вернула ненулевой код**, теоретически она выполнится дважды — в крайнем случае выключение или выход из сеанса могут повториться один раз. Это принято, потому что наполовину неудавшемуся действию питания попытка с правами нужнее, а лишнее выключение дешевле, чем машина, которая никогда не выключается.

## 5. Эндпоинты

Префикс `/api/dsh-shutdown-guard`, доступно только с локальной машины.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/state?since=<ms>` | полное состояние + инкрементальные события |
| GET | `/events?since=&limit=` | поток событий |
| POST | `/arm` `/disarm` `/cancel` | включить режим / снять / отменить текущий отсчёт |
| POST | `/config` | изменить **поведение**: профиль, переключатели, язык, операции с библиотекой скриптов |
| POST | `/ui` | изменить **внешний вид**: стиль карточки на боковой панели, тема, язык, компактный режим плавающего окна |

`/config` и `/ui` — две точки записи на одном HTTP-сервисе, разделённые по «поведение / внешний вид», потому что два слоя данных лежат в разных файлах и потребляются разными интерфейсами:

- `/config` пишет `data/config.json`. Принимает `customEnabled`, `activeProfileId`, `language`, `profileId` + `patch` (а также `afkAutoAnswer` верхнего уровня) и ключи библиотеки скриптов `putScript`, `selectScript`, `renameScript`, `deleteScript`, `ackScript`, `unackScript` (см. 4.1), а также `recheck:true` для повторной проверки доступности действий (см. 4.4).
- `/ui` пишет `data/ui.json`. Принимает `variant` (`A`/`B`/`C`), `theme` (`auto`/`dark`/`light`/`claude`), `lang` (`auto`/`zh`/`en`/`ru`), `compact` (булево).
- `/ui` отклоняет `notify`: уведомления — это поведение, а не внешний вид, возвращается `400 {"error": "notify belongs to the active profile; use /config updateProfile"}`.

**Профиль по умолчанию зафиксирован**. Запись любого из перечисленных ниже полей в `default` даёт 400:

```
{"error": "default profile is locked: <field> cannot change"}
```

Значения `<field>`: `countdownSec`, `marginSec`, `onlyOnSuccess`, `blockOnJobs`, `afkAutoAnswer`. Чтобы менять их, сначала создайте пользовательский профиль.

Прочие ошибки: недопустимый язык `400 unknown language`, неизвестный профиль `400 unknown profile`, неизвестный скрипт `400 unknown script`, POST с нелокального Origin `403`, метод не POST `405`.

Запись старых полей отклоняется явно, а не игнорируется молча — иначе бета-клиент решил бы, что загрузка или подтверждение прошли:

| Что записывают | Ответ |
| --- | --- |
| `patch.script` | `400 script must be uploaded through the script library` |
| `patch.scriptAck` | `400 scriptAck can only be written by acknowledging a library script` |

### Поля `/state`, связанные со слоем действий

| Поле | Форма | Описание |
| --- | --- | --- |
| `actions` | `{ [id]: { available, reason } }` | перечислены все 8 id, включая `restart-dsh` с дефисом; после монтирования и до первой проверки — `{}` |
| `actionReady` | bool | доступно ли `action` текущего профиля (`available !== false`); `'unknown'` считается доступным |
| `script` | объект \| null | метаданные записи, которую использует текущий профиль (`name` / `ext` / `bytes` / `sha256` / `savedAt`); **без тела и без имени файла** |
| `scriptAckOk` | bool | подтверждена ли текущая запись и совпадают ли всё ещё байты |
| `scripts` | массив | метаданные всей библиотеки, каждая `{ id, name, ext, bytes, sha256, savedAt, ackOk, ackAt, usedBy }`; тела там тоже нет |
| `lastAction` | объект \| null | последняя реально отправленная этим процессом команда, только для диагностики; `{ action, at, argv, code, failed, error?, elevated? }` |
| `lastAction.failed` | bool | вердикт по этой команде: ненулевой код или ошибка самого spawn. «Выполнилась» и «сработала» — разные ответы, это поле отвечает только за второй |
| `lastAction.elevated` | bool (может отсутствовать) | `true` только если был повтор через `pkexec` в Linux; без повтора ключа нет — не читайте это как `false` |
| `parkedAt` | число \| null | время начала приостановки выключения (только при `halted`), см. раздел 2 |
| `shutdownOnHaltEffective` | bool | производное правило из раздела 2 |

`script` / `scriptAck` внутри `profiles[]` — **совместимое представление**: они собираются из библиотеки по `scriptId` этого профиля, чтобы страница настроек могла отрисовать одну строку, не обходя `scripts[]`. Источник истины — верхнеуровневый `scripts[]`.

Ручная точка повторной проверки — `POST /config {"recheck": true}`: немедленно заново запускает проверку доступности и обновляет `actions`, **опроса нет**.

### Контракт отказа `/arm`

Когда действие выполнить нельзя, `POST /arm` **не** взводит режим с последующим провалом, а сразу отказывает: **409**, тело `{ error: <reason>, ...statePayload() }` — полный снимок состояния всё равно приходит, а `armed` остаётся `false`. Значение `error` берётся из `armRefusal()`:

| `error` | Когда |
| --- | --- |
| `no-script` | `action: custom`, но скрипт не выбран или выбранный файл удалён |
| `script-not-acknowledged` | выбранный скрипт не подтверждён, или байты на диске отличаются от подтверждённых |
| `reason` проверки этого действия | проверка уже признала его недоступным (`no-custom-profile`, `missing-interpreter`, `no-cli`, …) |
| `action-unavailable` | запасной вариант: конкретной причины нет, но действие действительно невыполнимо |

Интерфейс показывает эту причину отказа вместо переключателя, который делает вид, что режим включён.

## 6. Стратегии повторов

Каждому коду ошибки назначается имя стратегии, а сами стратегии настраиваются:

| Стратегия | Ритм по умолчанию | Назначена |
| --- | --- | --- |
| `rate-limit` | backoff 30 → 60 → 120 → 240 → 300 с потолком | `RATE_LIMIT` |
| `transient` | фиксированные 20 секунд | `SERVER` / `TRANSPORT` / `TIMEOUT` |
| `empty` | фиксированные 30 секунд | `EMPTY_RESPONSE` |
| `offload` | фиксированные 5 секунд | `IMAGE_OFFLOAD_REQUIRED` |

Ограничение частоты использует backoff, а не фиксированный интервал, потому что частые повторы к сервису с ограничением **продлевают** период ограничения, а не просто тратят запросы; восстановление после 5xx и сетевых сбоев предсказуемо по времени, и фиксированный интервал оказывается быстрее; выгрузка изображений — локальная операция с диском, повтор возможен почти сразу.

Переопределение отдельного кода ошибки:

```yaml
retryAssign:
  RATE_LIMIT: slow-limit
retryPolicies:
  slow-limit: { mode: backoff, base: 60, max: 900 }
```

Неизвестный `code` откатывается к `transient`; стратегия с неверной формой отбрасывается, а значение по умолчанию сохраняется. Действующие назначения можно прочитать из `retryAssign`, `retryPolicies` в `/state`.

**Нет таймера — нет обещания повтора**: если хост не может дать таймер, `retryAt` выставляется в `0`, в журнал пишется одно событие `log.retryUnavailable`, а интерфейс перестаёт показывать «повтор через N секунд». Лучше сказать «автоматического повтора не будет», чем показывать обратный отсчёт, который никогда не наступит.

## 7. Где хранятся предпочтения интерфейса

| Предпочтение | Где хранится | Ключ |
| --- | --- | --- |
| Стиль карточки на боковой панели / тема / сворачивание | браузерный `localStorage` | `dsh-shutdown-guard.variant` / `.theme` / `.folded` |
| Язык / компактный режим плавающего окна / четыре вида уведомлений | хост | `data/ui.json` (`notify` фактически попадает в профиль) |
| Всё поведение, связанное с профилем | хост | `data/config.json` |

`localStorage` изолирован по разделам хранилища (боковая панель и плавающее окно могут быть в разных разделах), поэтому состояние, в котором «оба интерфейса должны совпадать», — язык, компактный режим — держит хост и отдаёт его как `ui` в каждом `/state`; `localStorage` служит лишь запасным вариантом для первой отрисовки.

## 8. Миграция schema

- Текущая `CONFIG_VERSION = 5`. При чтении сначала смотрится `version`: всё меньше 5 разбирается по старой структуре, затем записывается обратно как `version: 5`.
- v2 → v3 ввела `parked` и переключатели уведомлений по профилям; v3 → v4 заменила никогда не публиковавшийся `customArgv` на **скрипты** (это поле недолго существовало только в рабочей ветке 1.6.1, и ни одна выпущенная версия его не записывала, поэтому перенос не делается); v4 → v5 перенесла «один скрипт на профиль» в **общую библиотеку верхнего уровня**.
- **Перенос v4 → v5** (2 / 3 / 4 обновляются сразу до 5):
  - Метаданные `script` каждого профиля становятся записью библиотеки, файл переименовывается из `<profileId>.<ext>` в `<scriptId>.<ext>`, а в профиле остаётся только `scriptId`.
  - **Старые файлы с одинаковыми `sha256` и `ext` сливаются в одну запись**, дублирующиеся копии удаляются, подтверждение (`scriptAck`) переезжает на объединённую запись.
  - Сразу после переноса выполняется **немедленная запись на диск**: `scripts[]` и переименованные файлы должны лечь вместе; если ждать следующей записи пользователя, при убийстве процесса останутся файлы, на которые никто не ссылается.
- Старые `profiles[]` сохраняются как есть: id не меняются, записи не разделяются и не переупорядочиваются, **изменённые вами вручную значения не теряются**.
- Новые поля (`action`, `scriptId`, `shutdownOnHalt`, `scripts`, `scriptSeq`) при отсутствии заполняются значениями по умолчанию: `shutdown` / `null` / `true` / `[]` / `0`.
- В файлах v2 нет поля `parked`, при чтении оно равно `null` (эквивалент «картины приостановки нет»); старого состояния для переноса нет.
- Ключи вроде `afkAutoAnswer`, `notify`, которые когда-то были и на верхнем уровне, и в профиле: приоритет у значения внутри профиля, старое значение верхнего уровня принимается только когда в профиле значения нет.
- При обновлении пустые слоты профилей, которых никогда не касались, очищаются; профиль, у которого меняли имя или трогали любой переключатель, сохраняется обязательно.
- Перенос идёт по полям и идемпотентен: после переноса поля `script` больше нет, поэтому повторное чтение не импортирует его второй раз.

## 9. Журнал событий

`data/events.log` — человекочитаемый поток с дописыванием, категории `config` / `afk` / `skip`; «Журнал событий» на вкладке «Состояние» страницы настроек читает именно его. Журнал уровня процесса лежит отдельно в `<DSH_HOME>\dsh-shutdown-guard.log`.
