# Release Notes 写作规范

适用于仓库根目录的 `RELEASE-<版本>.md`。目标只有一个：**用户能在 30 秒内判断「要不要升、升了会撞到什么」**。

`CHANGELOG.md` 是给维护者看的完整流水账；`RELEASE-*.md` 是给下载者看的一页纸。两者内容可以重叠，但写法不同——本规范只管后者。

---

## 一、骨架

照抄下面这个空模板，把尖括号里的内容换掉：

```markdown
# Shutdown Guard v<X.Y.Z>

一句话主题：这一版最重要的一件事，加一句它为什么重要。最多两行。

## 升级必读

- **<会咬人的变更>**：<触发条件>；<不改会怎样>；<怎么办>。

## `+` 新增

- `+` **<功能名>**：<用户能感知到什么> + <为什么值得加>。

## `-` 移除

- `-` **<被移除的东西>**：<现在用什么替代>。

## `~` 变更

- `~` **<变化名>**：以前<怎样>，现在<怎样>。

## 修复

- <坏了什么> → <现在怎样>。

## 兼容性与已知限制

- **<限制名>**：<在什么条件下会怎样>；<是否需要用户做什么>。

## 验证

发布前跑过：<实测数字>。

---

完整变更记录见 [CHANGELOG.md](CHANGELOG.md)。
```

小节按上面的顺序出现；某一节为空就整节删掉，不留空标题。

---

## 二、符号

| 符号 | 含义 | 判断标准 |
| --- | --- | --- |
| `+` | 新增 | 以前没有、现在有；用户能找到它 |
| `-` | 移除 | 以前有、现在没有；用户会找不到原来那个东西 |
| `~` | 变更 | 功能还在，但行为变了；不改符号就写不清楚 |

**为什么符号要包在反引号里、并且前面还有一个 Markdown 列表符**：行首的 `+` 和 `-` 在 Markdown 里会被当成列表标记，渲染出来根本看不见符号；写成 `` - `+` **名称**：… `` 才能让符号在页面上是「符号」而不是「圆点」。`~` 没有这个冲突，但为了三行看起来一致，统一加反引号。

**`~` 的判定**：如果一个改动既能让老用户「咦，怎么不一样了」，又没法用 `+` / `-` 说清，它就是 `~`。典型是默认值变化、取数口径变化、持久化位置变化。

**同一件事只出现在一处**：破坏性变更最多出现两次——`升级必读` 里一句话，`~` 小节里讲细节。不要在三处重复说同一句话。

---

## 三、每条怎么写

### 一行一条

一条目一行，写完就换行。超过两行说明你在写设计文档，不是在写 release note——把细节留给 `CHANGELOG.md` 或代码注释。

### 同一功能聚在一起

按**功能类型**分组（窗口、配置、设置页、主题、通知……），同一类型写在一起。**不要按提交时间排**，也不要把同一功能的 `+` 与 `~` 拆到两个不相干的位置。

### 写用户能看见的

- 写「设置页多了三张带缩略图的卡片」，不写「新增 `THUMB_B64` 内联数据」。
- 不写内部标识符：函数名、CSS 变量名、状态字段名、IPC 事件名一律不出现。
- 不写提交哈希、文件路径行号、PR 编号。
- 专有名词与产品名照产品里的写法，不自行翻译（如 `Claude Style`、`DeepSeek 蓝`）。

### 数字

- **测试条数与文件数必须精确**，因为用户可以自己核对。
- **体积、耗时、百分比一律取整到同一档**，不写小数点：写「约 360 kB」，不写「358.5 kB」。
- 数字必须来自实测，不许估。实测命令见第五节。

### 不做没有依据的断言

不写「不影响性能」「无感知」「更快了」，除非有实测并且写清怎么测的。没有就只写用户可核对的事实（包变大了、首次加载会多一点）。

## 四、升级必读

只有三条位置，宁缺毋滥：**只放会咬人的**。判断标准是「用户不读这一条，升级后会不会踩坑」。

每条必须同时具备三件事：

1. **触发条件**：什么情况下会遇上（自动发生 / 改某个字段 / 回退版本）；
2. **不改会怎样**：后果要具体到用户能想象的画面（报错 400、配置读不回来、通知全没了）；
3. **怎么办**：一句可执行的动作（先备份、新建一份配置、不用管）。

反例与正例：

| 别写 | 写成 |
| --- | --- |
| 「配置文件格式有调整。」 | 「配置文件会在下次保存时写成 v2：老文件自动兼容；但保存过一次后，用旧版打开可能读不回来。要回退，请先备份 `data/config.json`。」 |
| 「默认配置逻辑优化。」 | 「默认配置现在是只读的：改它的倒计时或判定开关会返回 400，并说明哪个字段不能改。要自定义，请点「＋ 新建」建一份自己的配置。」 |
| 「新增通知开关。」 | （这不是坑，移到 `+` 小节。除非它会改变用户已有的设置，才放这里，并写清「升级后沿用原来的总开关状态」。） |

三条满了还想加，优先删掉「后果只是有点不习惯」的那条。

## 五、数字从哪来

发布前在仓库根目录跑，把输出原样记下来：

```bash
node test/host.test.mjs     # 看最后一行 PASS: 后面的项数
node test/client.test.cjs   # 同上
npm.cmd pack --dry-run      # 看 total files / package size / unpacked size
```

PowerShell 下 `npm` 会因执行策略拒绝 `.ps1`，必须用 `npm.cmd`；并且不要让 npm 的 stderr 进管道，用 `*> 文件` 重定向，否则会被判成 NativeCommandError（命令其实成功了）。

写进「验证」小节的格式：

> 发布前跑过：宿主断言 43 项全绿（<覆盖了什么>），客户端 14 项通过（<覆盖了什么>）。

## 六、发布前检查单

- [ ] 标题版本号 == `package.json` 的 `version` == 即将打的 tag（去掉 `v`）
- [ ] `升级必读` ≤ 3 条，每条都能回答「不改会怎样」
- [ ] 没有一节的条目是空的；空节已删
- [ ] 每条一行；同功能聚在一起
- [ ] 没有内部标识符、提交哈希、行号
- [ ] 数字全部实测，体积类已取整、无小数点
- [ ] 没有「不影响性能」这类无依据断言
- [ ] 破坏性变更没有在第三处重复
- [ ] 升级方式里的版本号与标题一致
- [ ] 文末指向 `CHANGELOG.md`

---

## 七、把旧版说明转成新格式

已有的 `RELEASE-*.md` 不必重写内容，只做三步：

1. 原「新增」逐条加 `` `+` `` 前缀；一条里混了「新增 + 移除 + 行为变化」的，**按句子拆开归位**（例如「原来那条槽位快捷条已移除」属于 `-`，留在 `+` 里就不对）。
2. 原「行为变更」逐条改 `` `~` ``，并在 `升级必读` 里保留一句话版本。
3. 「已知限制」并入「兼容性与已知限制」，原「升级后建议做的三件事」如果只是操作指引，可以删——它属于文档，不属于 release note。

示范见 `RELEASE-1.6.0.md`。
