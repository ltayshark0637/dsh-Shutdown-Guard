# Руководство по участию

> [中文](CONTRIBUTING.md) · [English](CONTRIBUTING.en.md) · **Русский**

Спасибо, что готовы потратить время. Этот плагин написан под конкретный сценарий — «задачи закончились, пора выключить машину», — кода в нём немного, но несколько ограничений сделаны намеренно: прочитать этот файл до начала работы проще, чем получить пул-реквест обратно на доработку.

## 1. Какие пул-реквесты приветствуются

**Приветствуется:**

- **Исправление багов**, с шагами воспроизведения в описании пул-реквеста (какое состояние, что нажали, что ожидали, что получили).
- **Добавление утверждений**: если поведение сейчас ничем не прикрыто, покрыть его тестом — чистый выигрыш.
- **Исправление документации**: ошибки, устаревшие места, нерабочие примеры — всё считается.
- **Улучшения производительности и удобства**: отрисовка карточки, обновление плавающего окна, взаимодействие на странице настроек.
- **Поддержка новой платформы для действия**: например, более подходящая команда блокировки на каком-то дистрибутиве.

**Не принимается** (закрывается сразу, и дело не в тоне):

- **Добавление сторонних зависимостей.** **Ноль runtime-зависимостей** — жёсткое требование: на серверной стороне только `node:fs` / `node:path` / `node:crypto`, на стороне браузера только `require('react')`. Один лишний пакет ломает принцип «поставил и работает в любом окружении DSH».
- **Изменение `.github/workflows/publish.yml`.** За релизный конвейер отвечает мейнтейнер, внешние изменения не принимаются.
- **Изменение номера версии или раздела версии в CHANGELOG.** Версии пишутся централизованно при релизе; правка в пул-реквесте конфликтует с чужими изменениями.
- **Правка текстов только на одном языке.** Пул-реквест без перевода заставит один язык отображаться текстом другого, а это хуже, чем не менять ничего.
- **Добавление `process.exit()` в хост-процесс.** Оно пропускает очистку хоста и может испортить работающие сеансы; если нужен выход, идите существующим путём действия.

## 2. Что прочитать сначала

Перед началом прочитайте по необходимости эти три файла — это сэкономит большую часть переписки:

- [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) — пять шлюзов, машина состояний, почему отсчёт ведёт сам плагин.
- [`docs/CONFIG.md`](docs/CONFIG.md) — структура `data/config.json`, поля профиля, HTTP-эндпоинты, перечисление `reason`.
- [`docs/DEVELOPING.md`](docs/DEVELOPING.md) — как подключить локально, почему после изменений нужен полный перезапуск DSH, где лежат журналы.

## 3. Структура репозитория

Проще всего ошибиться, решив, что «тексты лежат в файле i18n». Три точки входа и их зоны:

- **`lib/index.mjs`** — хост-сторона: шлюзы, отсчёт, таблица действий, `/state` и остальные HTTP-эндпоинты.
- **`lib/client.js`** — клиентский bundle: карточка на боковой панели, страница настроек, плавающее окно. **Один файл, собран вручную, без шага сборки**; CSS и React — в этом же файле; изменения в нём вступают в силу только после полного перезапуска DSH.
- **`lib/i18n.mjs`** — каталог сообщений **хоста** на трёх языках (журнал событий, уведомления — тексты, которые отправляет сервер). **Клиентские тексты лежат в `MSG` внутри `lib/client.js`, а не в этом файле**.

## 4. Окружение

- Node **≥ 22.19** (нижняя граница зафиксирована в `engines` в `package.json`).
- **Без сторонних зависимостей**: `npm install` нужен только для того, чтобы дерево зависимостей существовало при запуске скриптов; шага сборки нет, каталога `dist` тоже.
- Платформы: Windows полностью проверен; macOS / Linux реализованы, но на реальном железе ещё не проверялись (см. известные ограничения в [`docs/BETA.md`](docs/BETA.md)).

## 5. Запуск тестов

Нужно запускать оба, из корня репозитория, и оба должны завершиться с exit 0:

```bash
node test/host.test.mjs     # утверждения хоста, ctx замокан, реального выключения нет — сейчас 66 пунктов
node test/client.test.cjs   # smoke клиентского bundle, настоящий client.js на фейковом React — сейчас 15 пунктов
```

`npm test` запускает оба подряд, это эквивалентно. После изменения `lib/*` нужно перезапускать оба; если менялись только документация или скрипты скриншотов, достаточно `client.test.cjs` (стили карточки и скриншоты берутся из одного источника).

Ещё одна команда, которая пригодится (при изменении стилей карточки):

```bash
node scripts/gen-gallery.cjs                                              # создаёт docs/screenshots/*.html
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/screenshot.ps1  # рендерит PNG, нужен Edge
```

## 6. Требования к утверждениям

Это самый важный раздел; если следовать ему, сэкономите один цикл переработки.

- **Новое поведение должно идти с утверждением.** Пул-реквест без утверждения попросят его добавить, даже если сама функциональность верна — поведение без утверждения означает, что никто не заметит, когда следующий человек его сломает.
- **Исправление бага требует обратной проверки**: верните исправление в исходное состояние и убедитесь, что утверждение краснеет. **В описании пул-реквеста приведите, на какой строке краснеет после отката и каковы actual / expected.** Это принятая в проекте практика (так проверяется каждый фикс бага), а не дополнительное требование.
- **Имена утверждений — в стиле `xxx-ok`**, одно имя на одно поведение, например `parked-clear-ok`, `custom-hidden-without-profiles-ok`. По имени должно читаться, что именно оно гарантирует.
- В сообщении утверждения указывайте фактическое значение при сбое, чтобы ошибку было видно без чтения кода.

## 7. Правило трёх языков

Поддерживаются `zh` / `en` / `ru`, **наборы ключей должны совпадать**:

- Добавляете текст — добавляйте во все три; удаляете — удаляйте во всех трёх. Пул-реквест только с одним языком будет возвращён.
- Каталог хоста проверяется утверждением `i18n-coverage-ok` по каждому языку — имена и количество ключей (`test/host.test.mjs`); не хватает одного ключа — тест краснеет.
- Тексты в клиентском `MSG` проверяются `test/client.test.cjs`: все метки страницы настроек должны присутствовать.
- Перевод должен читаться как человеческий текст, без машинного стиля; один и тот же концепт — одно и то же слово во всех трёх языках, не «включение режима» в одном месте и «запуск» в другом.

## 8. Коммиты и ветки

- **Один коммит — одно дело.** Исправление бага и попутный рефакторинг разделяйте: и ревью, и откат станут намного проще.
- **Сообщение коммита**: `type(scope): описание строчными английскими буквами`, `type` из `fix` / `feat` / `docs` / `test` / `chore` / `ci`, `scope` необязателен (`client`, `config`, `readme`, `release`…). Пример: `fix(client): hide the script rows when custom profiles are off`.
- **Не используйте `git add .`**. При совместной работе он затягивает чужие незакоммиченные изменения — этот репозиторий уже наступал на это дважды; теперь всегда `git commit -m "…" -- <явные пути>`.
- Пул-реквест делается от `main`. Для крупных изменений (контракт, машина состояний, формат данных) **сначала откройте issue для согласования**, чтобы не оказалось, что направление не то, уже после написания. В issue приложите: шаги воспроизведения, относящийся к делу фрагмент `data/events.log` (с вычищенными чувствительными данными), ответ `GET /api/dsh-shutdown-guard/state`, версии DSH и плагина.
- Не форматируйте попутно посторонние файлы: задетые пробелы, кавычки и отступы превращают diff в шум, и такие правки попросят откатить.

## 9. На что смотрит ревью

- **Не говорит ли интерфейс пользователю неправду**: в видимом пользователю тексте не должно быть внутренних id, кодов состояния, имён функций, `[object Object]`. Страница настроек должна переводить строки протокола в человеческий текст.
- **Объясняет ли путь отказа причину**: недоступное действие должно нести `reason` и переводить его в человеческий текст, а не падать молча и не оставлять серую кнопку без объяснения.
- **Затронуто ли только то, что нужно**: посторонние комментарии, форматирование, перестановки будут отклонены.
- **Действительно ли тесты блокируют регрессию**: имена утверждений соответствуют содержимому, обратная проверка проведена.
- После слияния автор упоминается в `CHANGELOG.md` (под вашим GitHub-именем) — такова традиция этого репозитория.
